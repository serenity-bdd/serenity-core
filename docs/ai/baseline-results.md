## What stands out
1. **Failures are import and package mistakes, not design mistakes.** The code structure was sensible in every case. Models know the *shape* of Serenity but guess the *packages* for Screenplay classes.
2. **Screenplay + Selenium is the weak spot**: 0 of 3 compiled, across all three models. Page Objects and REST were the strongest.
3. **Opus's one stale-import failure matches the bug we just fixed in the docs** (`net.thucydides.core.annotations.*`). Its other 7 runs used the right package. The stale samples were probably a real contributor; this supports fixing them first.
4. **The Screenplay package layout is unintuitive** (`actors.OnStage`, `abilities.BrowseTheWeb`, `questions.Text`, `screenplay.annotations.CastMember`). A one-page import cheat sheet would address most of the Screenplay failures directly.
5. **Style detection (P08, unnamed):** all three models chose Screenplay without asking. Only opus's compiled. None asked which style the user wanted. (Prompt P09 would test asking explicitly and has not been run.)
6. **Smaller models fail more**: haiku's 5 failures were wrong packages, several in one file.

## Caveats
- n = 1 per cell. Do not quote the rates.
- The `h-cuke-sp` harness has no JUnit 4 on its classpath, so haiku P08's `@RunWith` failure reflects that choice. That harness choice is correct for current Serenity.
- Compile-only: the tests may still fail at runtime (wrong locators, waits, ability setup). C2 is not measured.
- Unmeasured: P09 to P12, mode B (agentic, where the model can compile and recover), the style-consistency and idiom checks (S1 to S4, I1 to I11) beyond what compile errors show.
- Models were run through the Claude Code CLI with tools, settings, MCP and slash commands disabled, from an empty directory. A check showed no CLAUDE.md or memory leaked in.

## Implications for the roadmap
- **WS1/WS2:** put a Screenplay import cheat sheet at the front of the Screenplay guidance. Include the exact packages above and the `Collection<String>` return type.
- **WS6:** keep fixing stale samples and docs (done for the starter and the REST tutorial; the same snippets also exist in other docs pages).
- **WS7:** error messages cannot help here, since these are compile errors. Better IDE/auto-import discoverability might (for example, consistent package names).
- **Next measurement:** repeat with 3 runs per cell to confirm the Screenplay + Selenium result, then run mode B to see whether a compile loop fixes these (it probably does, since the errors are mechanical). The value of guidance is highest if mode B does *not* recover quickly.

# Pilot 2: Agentic mode (mode B)

The model works inside the prepared harness project with Write, Edit, Read, Glob, Grep and `mvn`, and may iterate. Told not to run tests (no browser) and to stop once `mvn -o -q test-compile` passes. One run per prompt per model (24 runs). Raw streams and produced sources: `eval/results/agentic-1/`.

## Result
All 24 runs compiled. The compile loop fixed every error that broke the one-shot runs.

| Model | Compiled | Avg `mvn` runs | Avg turns | Cost (8 runs) |
|---|---|---|---|---|
| opus-5-5 | 8 / 8 | 3.4 | 13.8 | $1.86 |
| sonnet-5-5 | 8 / 8 | 3.8 | 12.6 | $0.89 |
| haiku-5-5 | 8 / 8 | 5.6 | 21.5 | $0.14 |

Hardest cases (most compile attempts and turns): Screenplay + Playwright (P05: 8 to 10 `mvn` runs for every model), Cucumber (P07, haiku 8, opus 5), and Page Objects + Playwright with opus (P03, 6). Easiest: REST and Page Objects + Selenium (1 to 2 runs).

## How the agents found the right classes
- 17 of 24 runs listed `~/.m2` to see which Serenity and Selenium artifacts exist.
- 12 of 24 inspected jars with `javap` or `unzip` to find class names and signatures. In other words, agents work out the package layout by reverse-engineering the jars when the docs don't help them.
- 0 runs touched this repo's source. One run tried `WebFetch` and was denied (not in the allowed tools).

## What this means
1. **Guidance matters for efficiency, not correctness, when a compile loop is available.** The errors are mechanical and agents fix them. The cost is extra iterations (Screenplay + Playwright took 8 to 10) and, for smaller models, many more turns.
2. **The value of an import cheat sheet and an API catalogue is fewer iterations and less jar-spelunking**, not the difference between working and broken code. This lowers the priority of the failure-hint work and raises the priority of anything that avoids a round trip (for example, a catalogue, WS4).
3. **Cheaper models do work, with more steps** (haiku: 8/8 compiled for $0.14 total versus $1.86 for opus).

## Caveats
- Compile only: the tests were not run. A compile loop proves nothing about runtime correctness (locators, waits, ability setup).
- n = 1 per cell.
- **Design flaw for P08 (unnamed):** the runner always started it in the Screenplay web harness (`h-sp-selenium`), so the model did not choose the style. This run does not measure style detection. Fix before reusing.
- Tool access was Bash (broader than `mvn` in practice; the permission mode allowed read-only shell commands), plus file tools. A real project agent would have similar access.

## What changed from the pilot
- **Screenplay + Selenium is confirmed as the weakest style, but it is model-dependent**: opus compiled 3/3, sonnet and haiku 0/3 each. The pilot's "0/3 for every model" was a sampling artefact for opus.
- **Page Objects + Playwright is reliably fine** (9/9), but note that the demo module's API is small and distinctive.
- **Page Objects + Selenium is not as safe as the pilot suggested** (10/18; sonnet 5/6, haiku 2/6, opus 3/6).
- Model ranking is stable: opus > sonnet > haiku.

## Recurring errors (31 failed runs analysed; counts are runs)
| Error | Runs | Correct form |
|---|---|---|
| `BrowseTheWeb` imported from `net.serenitybdd.screenplay.webdriver` (package does not exist) | 8 | `net.serenitybdd.screenplay.abilities.BrowseTheWeb` |
| Generic mismatch: assigning `Text.ofEach(..)` to `Question<List<String>>`, or `Collection` to `List` | 8 | `Text.ofEach` returns `Question<Collection<String>>` |
| `.viewedBy(actor)` on a question, e.g. `Text.of(..).viewedBy(actor)` | 5 | Old UIStateReader API (the now-deprecated `UIStateReaderBuilder` family). Current style: `actor.asksFor(Text.of(..))` or `Text.of(..)` as a `Question` |
| `DefaultUrl` imported from `net.thucydides.core.annotations` | 4 | `net.serenitybdd.annotations.DefaultUrl` |
| JUnit 4 `@RunWith` / `org.junit.runner` | 3 | JUnit 5 extension, or JUnit Platform Suite for Cucumber |
| `ScenarioSteps` imported from `net.serenitybdd.core.steps` | 2 | `net.thucydides.core.steps.ScenarioSteps` (a case where `net.thucydides` is the *right* package) |
| `OnlineCast` from the wrong package | 2 | `net.serenitybdd.screenplay.actors.OnlineCast` |
| `@Page` imported from `net.serenitybdd.annotations` | 2 | no such annotation in this codebase (invented API) |
| `Navigate` from `net.serenitybdd.screenplay.navigation` | 1 | does not exist for Selenium; a `Navigate` exists in the Playwright module only |
| `Instrumented` imported as a class | 1 | static method `Tasks.instrumented(..)` |

## Findings
1. **Two kinds of error: wrong package (import guesses) and stale or invented API.** The agentic pass shows both are fixable by a compile loop, but they cost iterations.
2. **The `.viewedBy()` failures are stale-knowledge evidence from the API itself.** The deprecated `UIStateReaderBuilder` classes found in the first (abandoned) deprecation scan are exactly what models still reproduce. So deprecation data is useful *when cross-referenced with observed errors*, which is what this run did.
3. **Not everything under `net.thucydides` is stale**: `ScenarioSteps` lives there, and models wrongly moved it to `net.serenitybdd`. A blanket package-rename rule would be wrong in both directions. Guidance must name exact classes.
4. **One stale package still appears** (`DefaultUrl`, 4 runs). Given the docs bug we fixed, it's worth re-checking other docs pages and samples for the same pattern.
5. **Screenplay package layout is the main problem area**: `abilities`, `actors`, `questions`, and `annotations` sub-packages are easy to guess wrong.

## Combined picture (one-shot vs agentic)
- One-shot: 41 / 72 compiled (57%). With a compile loop: 24 / 24.
- So guidance should be judged by how much it **reduces iterations and one-shot failures** (especially for the smaller models), not by whether the final code compiles.

## Correction: runtime setup and the Cucumber plugin name

While running the WS3 spike on a Cucumber project, the project failed at run time. Two things in the guidance and harness were wrong, and compile-only checks could not see either:

- The Serenity Cucumber plugin is `net.serenitybdd.cucumber.core.plugin.SerenityReporterParallel`, not `io.cucumber.core.plugin.SerenityReporterParallel` (the string appeared in the Screenplay reference, the Cucumber example, the `AGENTS.md` Cucumber variant and the docs pages). It is only a string, so the code still compiled.
- Serenity 5.4.1 depends on JUnit 6.1.3 and Cucumber 8.0.4. The harness pinned JUnit Jupiter 5.12.2, junit-platform-suite 1.12.2 and Cucumber 7.31.0, which compile but fail at run time with conflicting JUnit versions.

Fixed in the references, examples, `AGENTS.md` variants, harness generator (JUnit BOM 6.1.3, Cucumber 8.0.4) and the docs pages. All six example sets now also run: `check-examples.sh --run` ran their tests (headless Chrome, Playwright and the live sample sites) and all passed. The earlier compile rates in this file were measured against the old pins; Cucumber results in particular should be read with that in mind, and the Cucumber prompts re-run. None of the model-generated code in the evaluations has been run.

## Runtime stage: running the generated tests (`eval/run_tests.py`)

The tests that models generated were run for the first time: each run was rebuilt in a fresh copy of the harness (JUnit 6.1.3, Cucumber 8.0.4, surefire including every class) and run with `mvn verify`, headless Chrome and Playwright, against the live sample sites. A failed run is repeated once. Runs that don't compile count as not passing. Per-run records are in `results/*/runtime/` and `runtime.json`.

| Set (runs) | Unguided | Guided |
|---|---|---|
| Screenplay with Selenium, Playwright, REST (H01–H06, 54 runs) | **28/54 pass (52%)** | **48/54 pass (89%)** |
| Page Objects with Selenium, Playwright (H09–H13, 45 runs) | **35/45 pass (78%)** | **45/45 pass (100%)** |
| Cucumber with Screenplay (P07, H07, H08, 27 runs), corrected harness; guided with the corrected reference | **0/27** | **24/27 pass (89%)** |

- **Compiling code nearly always ran.** Of the runs that compiled, 28/28 (Screenplay, unguided), 48/49 (Screenplay, guided), 35/36 (Page Objects, unguided) and 45/45 (Page Objects, guided) passed. For these styles, compile rate was a good proxy for pass rate; the guidance's effect is on getting code to compile.
- **The three remaining non-Cucumber failures** were: a Playwright login test asserting exact text where the page adds a trailing symbol (a model error: `hasText` vs `containsText`), and one Selenium locator that matched nothing (`.primary_header .title`).
- **Cucumber was the exception, and the guidance was the cause.** The earlier held-out guided Cucumber runs (H07, H08: 0/18 at runtime) were generated with the reference that then named the wrong Serenity plugin class, and the models copied it. The unguided models also guess `io.cucumber.core.plugin.SerenityReporterParallel` (0/27 pass; even Opus). With the corrected reference, 24/27 pass. The 3 failures: two runs that still used the wrong plugin name (Opus), one `NullPointerException` in a Haiku step definition. Compile-only checks showed 26 to 27 of 27 for these runs in both cases; the run-time check is what exposed the difference.
- **A pointer for the docs:** the unguided Cucumber failures include "No BaseStepListener has been registered", the symptom of running Serenity step definitions without the Serenity plugin.

What the failures were:
- **A Serenity gotcha, not a model slip:** 5 of the 11 unguided failures (P04, P07 and P08, all Screenplay with Selenium) used `Target.the(..).locatedBy("input.new-todo")`. Serenity reads a locator string as XPath when it compiles as an XPath expression, and `input.new-todo` does (a name test), so the element is looked up as XPath and not found at run time. `.new-todo`, `#id` and `[data-x=y]` are read as CSS. The fix is `Target.the(..).located(By.cssSelector(..))`. The compile-only evaluation could not see this. It is now in the Screenplay reference (with a run-verified example), the Selenium and Cucumber `AGENTS.md` variants and the `llms.txt` header and docs pages.
- **Cucumber without the skill:** 0/6 for P07; the models guess the wrong plugin class (`io.cucumber...`), as in the one-shot runs.
- **Other:** one NPE from a driver that was never initialised (Haiku, unnamed prompt) and one `ClassCastException` in a REST test (Opus, with the skill).

Caveats: the seeded-project and Cucumber results depend on the repairs above; live sample sites; Claude 5.5 models; passing means the test ran green, not that it checks the right thing. The skill's advantage at runtime (98% vs 83%) is larger than at compile time, because the run-time errors are ones that compile.

### Follow-up: Playwright locator rules

The residual one-shot failures with guidance were concentrated in the four Playwright prompts (A03, A04, A07, A08). Compiling the failures showed that most (6 of the 8 inspected) came from the reference itself: it listed `Ensure.thatTheCurrentUrl()` and `Ensure.thatThePageTitle()`, whose return types are package-private in `serenity-screenplay-playwright` 5.3.11, so any call fails to compile. Two others were run-time strict-mode violations from selectors that match a list. The reference now says not to use the two `Ensure` methods (with the working alternative) and that a selector must match one element, with the list idioms; `playwright-checks/verify.py` runs five cases and `examples/sp-playwright/todo/ListTest.java` shows them.

| Four Playwright prompts, guided one-shot, 36 runs | Before | After the new rules |
|---|---|---|
| GOOD | 24 | **33** |
| Compile failures | 10 | **0** |
| Fail on the healthy app | 2 | 3 (a `todo is null` error copied from the example's names, and two Playwright timeouts in A08 by one model) |

A second reproduction of the two remaining Opus timeouts (A08) found their cause: both built a text pattern with `Pattern.quote(title)`, whose `\\Q..\\E` is not valid JavaScript regex, so the locator matched nothing and the step timed out. The reference now says to use a plain string or a hand-written pattern (`playwright-checks`, case `regex-quote`). Re-run of the same 36 runs: **36/36 GOOD** (Haiku, Opus and Sonnet 12/12 each; 9/9 on each prompt). The Haiku `todo is null` failure did not recur, so it was probably a one-off copy from the example rather than something the rules cause.

Caveat: these rules were written from failures on these same four prompts, so this is a repair measurement, not a held-out result (the same limit as the earlier Screenplay extension).
